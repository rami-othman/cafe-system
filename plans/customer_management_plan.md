# 1. Purpose

Build a production-ready **Customer Management** feature for Cafe System 618.

The feature must integrate safely with the existing Laravel backend, Flutter Windows/Web application, POS, Orders, Discounts, authentication, tenant isolation, and branch-access model.

This document is the **feature roadmap and brownfield context** to use when creating the Spec Kit specification.

It is not the final implementation plan generated by `$speckit-plan`.

# 2. Existing-System Facts From Phase 0 Audit

The current system already has a `customers` table, but Customer Management as an administrative feature does not exist.

Current customer behavior:

- `customers` currently stores:
  - `tenant_id`
  - `name`
  - one nullable `phone`
  - nullable `email`
  - birth date
  - notes
  - stored `total_spent`
  - stored `visits_count`
  - `is_active`
  - timestamps
  - soft delete
- There is no Customer Eloquent model/service/policy/CRUD controller.
- Current customer API is only:

```text
GET /api/v1/customers
```

- It is tenant-scoped.
- It returns active/non-deleted customers only.
- It supports simple name/phone `LIKE` search.
- It has a hard limit of 30.
- It has no pagination, status filtering, group filtering, or administration mode.

Current POS depends on the customer API fields:

```text
id
name
phone
email
totalSpent
visitsCount
loyaltyPoints
tier
```

Current POS behavior:

- Customer is optional.
- “Walk-in Customer” is valid.
- POS can select/clear a customer.
- POS cannot create/edit customers.
- POS initially loads customers and filters locally.
- Order create/update can attach `customerId`.

Current order behavior:

- `orders.customer_id` is nullable.
- Customer ID must belong to the tenant and not be soft-deleted.
- Current validation does not reject inactive customers if an ID is submitted directly.
- Historical order/report customer display currently resolves the **live current customer name/phone**.

Current discount behavior:

- Existing customer eligibility uses fixed tiers:
  - New Customers
  - Regular
  - VIP
- Tier logic is based on stored `total_spent` / `visits_count`.
- These tiers are **not Customer Groups**.
- Existing tier discount behavior must remain backward-compatible during Customer Management V1.

Current stored customer metrics:

- `total_spent`
- `visits_count`

are not currently maintained by the real order/payment lifecycle and must not become authoritative silently.

# 3. Non-Negotiable V1 Domain Decisions

## 3.1 Customer Scope

A Customer belongs to **exactly one tenant**.

Customers are tenant-wide, not branch-owned.

```text
Tenant
└── Customers
    ├── usable at Branch A
    ├── usable at Branch B
    └── usable at Branch C
```

A customer created/managed for one tenant must never be visible or usable by another tenant.

Do not introduce branch-scoped customers.

---

## 3.2 Customer Groups

Customer Groups also belong to exactly one tenant.

A customer may belong to zero or more groups.

Examples:

```text
Students
Staff
Family
Government Employees
Charity Members
```

Customer Groups are different from existing customer tiers.

A tenant discount may target a Customer Group and may apply to:

```text
All Branches
or
Selected Branches
```

but never across tenants.

---

## 3.3 Customer Tier vs Customer Group

Keep these concepts separate.

```text
Customer Tier
├── New
├── Regular
└── VIP

Customer Group
├── Students
├── Staff
├── Family
└── ...
```

Existing tier-based discount behavior must remain unchanged during Customer Management V1.

Do not replace tier rules with Customer Groups in this feature.

---

## 3.4 Walk-In Customers

Anonymous POS orders remain valid.

```text
order.customer_id = null
```

must continue to be supported.

Customer Management must not force every order to have a customer.

---

## 3.5 Customer Lifecycle

Use non-destructive lifecycle behavior.

Required states:

```text
Active
Inactive
Archived
```

Semantics:

### Active

- visible in operational customer lookup
- selectable in POS
- attachable to new orders

### Inactive

- remains historically valid
- not selectable for new operational use

### Archived

- hidden from normal operational/admin lists by default
- historical references remain intact
- may be restored

Hard delete must not be exposed as a normal Customer Management operation.

---

## 3.6 Operational Customer Eligibility

Define one authoritative backend rule for whether a customer may be attached to a new operational order.

Minimum requirements:

```text
same tenant
AND
not archived/deleted
AND
active
```

This rule must be enforced by backend order create/update logic, not only Flutter.

Customer lookup and order attachment must agree on the same rule.

---

## 3.7 Phone Compatibility and Multi-Phone Support

The current API and POS depend on:

```text
customers.phone
```

V1 must preserve backward compatibility.

Introduce a proper multi-phone structure:

```text
customer_phones
├── id
├── tenant_id
├── customer_id
├── raw_number
├── normalized_number
├── type
├── is_primary
├── validation_status
├── created_at
└── updated_at
```

Rules:

- A customer may have zero, one, or multiple phone numbers.
- Phone number is not a unique customer identity.
- Duplicate/shared phone numbers are allowed.
- Raw entered value should be preserved.
- Normalized phone is used for search.
- Exactly one phone may be primary when phones exist.

Backward compatibility:

```text
customers.phone
```

must continue to behave as the legacy/primary phone contract for existing POS/API consumers during the transition.

Do not remove or break the existing `phone` field in V1.

---

## 3.8 Customer Number

Introduce a tenant-scoped customer-facing number.

Suggested field:

```text
customers.customer_number
```

This is not the database primary key.

Legacy customer numbers will be handled later during the separate import feature.

---

## 3.9 Historical Customer Display

For V1, preserve current behavior:

```text
historical order
→ customer_id
→ current live customer name/phone
```

Do not introduce immutable customer snapshots into orders during this feature unless explicitly required by the Spec Kit specification after clarification.

Historical snapshot redesign is a separate concern.

---

## 3.10 Customer Metrics

New Customer Management metrics should be derived from authoritative order/payment data.

Examples:

```text
Total Orders
Total Paid Spend
Average Order Value
First Visit
Last Visit
Recent Orders
```

Do not silently repurpose stored:

```text
total_spent
visits_count
```

as authoritative analytics.

At the same time, do not change existing discount tier logic that currently depends on those fields.

# 3. Core Domain Decisions

## Customer Identity

Each customer belongs to exactly one tenant.

The internal database ID is authoritative for system relationships.

A customer must not be identified uniquely by phone number alone.

Phone numbers may be shared, duplicated, missing, or malformed.

---

## Customer Phones

Use a dedicated customer phone structure rather than fixed `phone`, `mobile`, `phone2` columns.

Suggested model:

```text
customer_phones
├── id
├── tenant_id
├── customer_id
├── raw_number
├── normalized_number
├── type
├── is_primary
├── validation_status
├── created_at
└── updated_at
```

Rules:

- A customer may have zero, one, or multiple phone numbers.
- Phone number uniqueness must not be globally enforced.
- Raw user-entered value should be preserved.
- Normalized value is used for search and duplicate detection.
- Only one phone may be primary per customer.

---

## Customer Groups

Customer groups are optional.

Suggested model:

```text
customer_groups
├── id
├── tenant_id
├── name
├── is_active
├── created_at
└── updated_at
```

Membership:

```text
customer_group_memberships
├── customer_id
└── customer_group_id
```

The schema should support multiple groups per customer even if V1 UI initially exposes a simpler workflow.

---

## Customer Lifecycle

Recommended states:

```text
Active
Inactive
Archived
```

Rules:

- Archive must not delete historical orders.
- Existing orders keep the customer reference.
- Archived customers may remain visible in historical contexts.
- Archived customers are not selectable for new POS orders unless explicitly restored.
- Restore should preserve historical customer identity.

# 10. Legacy Data Import — Deferred Until After Feature Completion

Legacy import is intentionally NOT part of the implementation phases above.

Only after Customer Management V1 is complete should a separate specification be created for:

```text
Legacy Customer Import
```

That future feature will cover:

- CSV decoding/parsing
- Legacy field mapping
- Legacy customer numbers
- Legacy account codes/names
- Phone normalization
- Customer group mapping
- Duplicate detection
- Dry-run
- Idempotent import
- Reconciliation report
- Import rollback/recovery strategy

No automatic customer merging should be performed purely from phone or name similarity.
